# 08 · 异常定位练习

状态：**3组已复现，待候选人定位分析；尚未实现对应修复。**

候选人提出先亲自定位，再交由AI修改。本练习提供独立资料、数据库与实际观察，不改动正式输入和原始验收Trace。默认使用离线Mock隔离业务数据问题，不产生API费用，也不证明模型决策效果。

## 复现入口

在仓库根目录执行：

```powershell
python scripts/debug_lab.py --case E01
python scripts/debug_lab.py --case E02
python scripts/debug_lab.py --case E03
```

不传case时运行全部。新报告写入 `runtime/debugging/reports/`，中间数据库在runtime内，均被Git忽略。提交中的首次快照见 [examples/exercises](../examples/exercises/README.md)。脚本退出表示演练执行结束，不表示业务成功或缺陷修复。

## 三个场景

| 编号 | 业务情形 | 当前实际现象 | 分析目标 |
| --- | --- | --- | --- |
| E01 | 接入一份外部费率表后，预算10需要评估替代档次 | TypeError，规划未保存 | 找到首次异常动作和输入差异，判断校验与错误回传应放在哪一层 |
| E02 | 素材库更新后，相关素材仍能检索到 | 生成阶段KeyError，规划未保存 | 区分检索成功与资料可供后续使用，定位缺失的数据契约 |
| E03 | 先完成一个请求，再用同一ID把预算10改成11 | STATE_CONFLICT，数据库保留首份方案 | 判断这是合理保护还是缺陷，说明重规划应如何标识新需求 |

专用覆盖资料位于 `data/debugging/`。未覆盖的文件使用正式合成资料。你可以对照资料、selected_actions、checkpoint_steps和异常frames；frames使用仓库相对路径，不包含电脑用户名或绝对路径。

## 建议排查顺序

1. 写出复现命令与预期行为，先区分“应当拒绝的业务请求”和“应当被明确处理的程序异常”。
2. 对照selected_actions与checkpoint_steps，找出最后成功的动作以及首次未形成正常观察的动作。
3. 根据相对路径和行号定位代码，再比较正式资料与演练资料，说明输入如何流向异常位置。
4. 提出最小修改范围：校验、工具结果、Runtime返回或请求使用方式，避免用吞掉所有异常掩盖根因。
5. 设计回归：原有正常链路仍可完成，异常应有明确错误与未完成状态；失败不能保存，成功结果应保留。

## 个人分析模板

把以下内容发回协作聊天，或另存为分析文档再提交。当前没有预填根因和修复结论。

```text
场景编号：
复现命令：
预期行为与实际行为：
最后成功步骤 / 首次异常动作：
定位文件、函数或行号：
根因分析及证据：
这是缺陷还是合理业务保护，为什么：
建议修改范围：
需要补充的测试与预期：
本人定位用时：
```

## 分析后的协作约定

候选人先提交定位结论；AI根据分析实现修改，保留演练前快照，生成修复后结果并补充必要测试。两者在AI使用与复盘中分别记录，不把AI实现的代码写成个人手工修改，也不提前宣称已完成定位或修复。
