# 05 · 复盘与下一步

## 难点

本复盘根据实际实现和运行记录整理。技术结论供候选人审阅确认，个人完成范围以AI使用说明为准。

需要让模型真正选择下一动作，同时确保模型不能通过伪造成本或一句“已完成”绕过工具事实。因此把动作选择交给模型，把费用、截止时间、依赖和保存成功判定放在服务端。失败成为下一轮观察，不由Runtime自动改成成功。

另一个难点是重复执行与失败续跑：成功脚本应该保留，失败步骤也必须保留，已保存方案只能有一份。采用请求指纹、SQLite唯一键和逐步断点，避免只靠内存状态证明幂等。

## 业务理解与设计取舍

任务目标是交付“可执行的内容方案”，因此任务拆解、费用口径和失败状态优先于界面。CLI足以展示完整链路，也便于评审替换预算、截止时间和故障输入。原生实现减少框架学习成本，使模型消息、工具反馈和数据库状态可直接检查。

模型擅长在观察后选择下一动作，成本计算和事务结果则需要确定性校验。预算10时，premium估算12不满足要求；模型选择standard后必须再次运行估算，不能把自然语言中的“便宜一点”直接视为成本8。只有工具证据支持且数据库提交成功，才能完成任务。

保留成功步骤既减少重复工作，也使失败可解释。保存失败时不重新检索和生成脚本，而是保留素材、脚本与估算；恢复后有机会从保存步骤继续。SQLite适合这个本地范围，但唯一键只保证不产生第二份方案，不代表整个系统已具备分布式并发安全。

## 实际发现与修正

系统临时目录权限导致文件测试失败，改用项目内部临时目录后通过。真实DeepSeek初次网络失败后按用户要求先交付并保留证据；后续重试成功，已完成真实决策验证，没有以Mock替代。

真实模型无素材时主动改写查询并追问，返回needs_input；原评估器只接受incomplete，导致首次12/13。修正规则时同时强化空检索、资料缺口和禁止编造结果的证据要求，并阻止网络错误混入业务负向用例。保留首次汇总和原始Trace，以带文件哈希的独立复核记录13/13。此次发现说明评估本身也需要验证，不是只看通过率数字。

追加异常输入后发现两类资料契约缺陷：费率将数字写成文本时直接参与求和，引发TypeError；检索成功的素材缺少facts时，脚本生成直接读取字段，引发KeyError。根因是只校验模型参数，没有在实际消费资料的工具中充分校验业务数据。现已增加类型、字段、有限值和日期范围检查，使错误作为结构化观察回传模型，而非中断整个执行。

另一个请求修改预算的“失败”被确认为正常保护：同一ID绑定输入指纹，改变预算应使用新ID。回归验证原方案保留、新ID能够创建新计划。此次没有为追求“全部成功”而删除幂等约束。

## 学习收获与待验证理解

1. Agent的价值在于观察反馈后的动作变化。固定调用顺序与自动重试可以作为执行基础，但不能单独证明模型决策。
2. 完成状态需要证据。“脚本生成成功”“估算可行”“方案提交成功”是不同节点；失败时必须说明具体缺口。
3. 测试也可能有缺陷。无素材时合理追问被原规则误判，修正时应保留原始结果并增强事实检查，不能只把预期改到通过。
4. 正常资料通过不代表外部资料健壮。新增10项回归验证资料契约，既检查错误状态，也检查未落库、成功结果保留和可用替代素材不被误伤。
5. `retryable:false`表示原资料与参数不变时重试无效。真实模型仍可换合法档次或素材；离线Mock选择明确停止，两者职责和验证范围需要分开说明。
6. 理解需要能对应具体函数、输入和Trace。根因记录已经补齐，候选人可通过保留的前后样例复现并验证自己的理解。
